# Ускорение CI, раунд 2: три задачи для агентов

Дата: 2026-10-24. Предыдущий раунд (path-filtered jobs, бандлы client и
server-unit, 3 pg-шарда, slim builder) смержен в `0f35d28a3`, детали — в
комментариях `.github/workflows/pipeline.yml` и `scripts/gen_test_bundles.py`.

Каждая задача ниже самодостаточна: её можно отдать отдельному агенту целиком.
Все три правят `.github/workflows/pipeline.yml`, поэтому **выполнять по очереди,
не одновременно**, в порядке 1 → 2 → 3 (порядок — по выигрышу на критическом
пути PR).

| 40092886976 | PR (без `ci:full`) | ~11 мин | test-client-a 672 с: codegen 203 с + тесты 449 с |
| 40069163370 | PR | ~9 мин | test-client-a 511 с: codegen 144 с + тесты 348 с |
| 40070447756 | push main | 10 мин 21 с | build-web 529 с (в эту работу не входит) |

Прочие задачи в тех же прогонах: test-client-b 371–388 с (codegen 173–199 с),
test-pg-1/2/3 ≈ 330–446 / 324–327 / 329–334 с (codegen 45–60 с), test-server
237–244 с, test-lints 50 с.

Вывод: на PR критический путь — **client-a**, и почти половина его — codegen.
pg-шарды на PR без метки `ci:full` вообще не запускаются; они важны для
`ci:full` и для push в main, когда клиент не менялся.

## Общие правила для всех трёх задач

- Читать `AGENTS.md` и `.claude/CLAUDE.md`. Локальные тесты — только через
  `scripts/run_tests.sh <profile>` или `scripts/run_with_test_cleanup.sh`
  (машинная очередь; не запускать тесты, пока работает Alloy). CI не
  оборачивать.
- Отдельная ветка на задачу, PR в `main`; в main напрямую не пушить. PR-режим
  пропускает pg-шарды: для задач, затрагивающих pg, повесить метку `ci:full`
  (`pr-full-ci.yml` перезапустит прогон целиком).
- Перед пушем — ревью диффа через codex (`gpt-6.1-sol`, effort high).
- Нельзя терять тесты. Для каждой изменённой выборки сравнить число
  выполненных тестов до/после (по логу `dart test`/`flutter test` или
  `--reporter json`). Расхождение = баг, а не «шум».
- Нельзя ослаблять тесты ради скорости: не трогать тайминги в
  `hung_pg_test_diagnostics`, race-раунды `post_lock_order` /
  `post_bud_concurrency`, attention sweep slow capture (обоснование — в
  истории предыдущего раунда).
- Результат каждой задачи: замеры из 2+ зелёных прогонов CI против таблицы
  выше и короткое описание в PR.

## Задача 1. Codegen в CI — сделать по-настоящему инкрементальным

### Проблема

Каждая задача CI (`test-shards`, а также `build-web` / `build-server`) сама
запускает `build_runner`. Кэш `codegen-<pkg>-<hash>` восстанавливается, но не
помогает. Лог test-client-a в прогоне 40092886976:

```
Cache restored from key: codegen-client-73e9e7e6…   (по restore-key, 12 MB)
Pulling from intersubjective/tentura-builder        12:11:52 → 12:12:17 (25 с)
Built with build_runner/aot in 163s; wrote 7185 outputs.
```

`wrote 7185 outputs` — это полная пересборка. Основная гипотеза (проверить
первой): кэшируется только `packages/<pkg>/.dart_tool/build`, а сами
сгенерированные файлы (`**.g.dart`, `**.freezed.dart`, `**.config.dart`,
`packages/client/lib/ui/l10n/*` — все в `.gitignore`) лежат в дереве исходников
и в кэш не попадают. На свежем checkout asset graph ссылается на выходы,
которых нет, и `build_runner` пересобирает всё. Другие возможные причины:
перекомпиляция build script (`build_runner/aot`), пересчёт package graph после
`pub get` с другими путями или mtime.

### Что сделать

1. Воспроизвести и **доказать причину** (локально: чистый клон →
   восстановить только `.dart_tool/build` → `dart run build_runner build` →
   посмотреть, сколько outputs пишется; затем то же самое с восстановленными
   сгенерированными файлами).
2. Исправить так, чтобы повторный прогон с тёплым кэшем писал только
   изменённые outputs. Вероятный вариант — класть в кэш вместе с
   `.dart_tool/build` и сгенерированные файлы. Список файлов брать из самого
   build_runner или как `git ls-files --others --ignored --exclude-standard`
   после сборки, а не hand-written glob, чтобы новый генератор не выпал молча.
3. Убедиться, что кэш остаётся корректным:
   - выходы для изменённых входов пересобираются (build_runner сверяет
     digests);
   - удалённый исходник не оставляет «осиротевший» сгенерированный файл,
     который маскирует ошибку компиляции;
   - PR не может отравить кэш main (кэши GitHub изолированы по веткам —
     подтвердить, что так и остаётся).
4. Подумать над параллельным `docker pull` builder-образа (25 с на каждую
   задачу): начать pull в фоне в начале задачи, до восстановления кэшей.
   Делать, только если выигрыш измерим.
5. Сейчас client-a и client-b одновременно пытаются сохранить один и тот же
   ключ (`Failed to save: Unable to reserve cache … another job may be creating
   this cache`). Это безвредно, но если схема ключей меняется, сохранять из
   одной задачи.

Не делать: коммитить сгенерированный код в репозиторий; выносить codegen в
отдельную предшествующую задачу с передачей артефакта. Такая задача
добавляет последовательную стадию, wall time не сокращает, а экономит только
runner-минуты. Это можно предложить отдельно, с цифрами, если после фикса
инкрементальности codegen всё ещё дорогой.

### Критерии приёмки

- На PR, меняющем 1–2 файла в `packages/client/lib`, шаг «Generate code in
  builder container» в test-client-a/b занимает ≤ 40 с (сейчас 144–203 с), в
  логе build_runner пишет порядка десятков outputs, а не тысячи.
- То же для server-задач: ≤ 20 с (сейчас 44–60 с).
- Холодный прогон (пустой кэш) по-прежнему проходит.
- Сгенерированное дерево после тёплой сборки побайтно совпадает с холодной
  сборкой того же коммита (проверить один раз вручную, описать в PR, как
  повторить).
- Ожидаемый эффект: PR-прогон короче на ~2–2,5 мин.

## Задача 2. Перебалансировать шарды: client 2 → 3+, pg 3 → 6

### Проблема

Шарды неравномерны, а критический путь определяет самый медленный:

- **client**: client-a 335–449 с тестов **плюс** анализатор
  (`check-analysis.sh packages/client`, ~100 с внутри шага), client-b 153–185 с.
  Разбиение по каталогам захардкожено в `pipeline.yml`: client-a берёт всё
  вне `test/features` плюс `beacon_threads`, `constellation`, `auth`.
- **pg**: 387 файлов с тегом `pg`, разбиты в `scripts/ci_select_tests.py`
  round-robin по отсортированному списку (`files[i-1::n]`), без учёта
  длительности. Шарды 249–373 с. `multi-connection` (17 файлов, `-j 1`)
  гоняется ещё и на шарде 2.
- Матрица собирается в задаче `changes` строками `shards+=…`
  (`pipeline.yml`, ~строки 140–175).

### Что сделать

1. **Вынести анализатор клиента в отдельный шард** (или в шард `lints`, если
   это не сделает его критическим путём). Анализатор и тесты не зависят друг
   от друга.
2. **client → 3 шарда (или 4, если замеры покажут выигрыш)** с балансировкой по
   измеренной длительности, а не по каталогам. Варианты:
   - разбивать бандлы `gen_test_bundles.py --chunks N` между шардами;
   - добавить в `gen_test_bundles.py` / `ci_select_tests.py` режим
     `--shard I/N` с жадной упаковкой по весам из закоммиченного файла
     длительностей (например `scripts/ci_test_durations.json`, файлы без
     записи получают медиану).

   Требование сохраняется: новый тестовый каталог или файл автоматически
   попадает в какой-то шард (сейчас это обеспечивает вычисляемый `find`).
   Добавить проверку в `scripts/test_ci_changes.py` или рядом: объединение
   шардов = полный набор, пересечений нет.
3. **pg → 6 шардов** с той же балансировкой по длительности.
   `multi-connection` оставить отдельным вызовом `-j 1` на одном шарде (самом
   лёгком после балансировки) или вынести в собственный шард, если он
   окажется критическим.
4. Описать, как обновлять файл длительностей (скрипт, собирающий его из
   `--reporter json` / `--file-reporter json:` CI-прогона), и что устаревший
   файл влияет только на баланс, а не на корректность.
5. Учесть лимит: у публичного репозитория 20 одновременных задач на бесплатном
   плане. Полный прогон после изменений: lints + server + 6 pg + 3–4 client +
   analyzer + build-web + build-server ≈ 14 — помещается, но запас небольшой.

### Критерии приёмки

- Число выполненных тестов по каждой выборке (client целиком, pg целиком,
  multi-connection) совпадает с базой.
- Тест на полноту/непересечение шардов есть и проходит в шарде `lints`.
- PR-прогон: максимум по client-шардам ≤ ~4 мин тестов (сейчас 5,5–7,5 мин),
  с учётом задачи 1 весь PR ≈ 5–6 мин.
- `ci:full`-прогон: максимум по pg-шардам ≤ ~3,5 мин шага тестов (сейчас
  4,1–6,2 мин).
- Разброс между самым быстрым и самым медленным шардом каждого семейства —
  не больше ~25%.

## Задача 3. Бандлы для pg-тестов в CI

### Проблема

`dart test` компилирует и запускает каждый тестовый файл отдельно. Бандлы
(`scripts/gen_test_bundles.py`) склеивают много файлов в один entrypoint: одна
компиляция — много файлов. Для client это дало client-b 541 → ~75 с, для
server-unit — 161 → 104 с. **pg-файлы сейчас из бандлов исключены
намеренно** — см. docstring `gen_test_bundles.py`:

> is tagged `pg` (server: per-suite tags drive the MeritRank suite lock)

Причина: `_isMeritRankSuite()` в `packages/server/test/support/disposable_pg_target.dart`
смотрит на теги **suite** (`Invoker.current?.liveTest.suite.metadata.tags`).
В бандле suite один, а теги файла переносятся на `group(...)`, поэтому
`mr`-файл в бандле потерял бы MeritRank-лок.

Изоляция БД уже подходит для бандлов: 374 из 387 pg-файлов используют
`disposable_pg_target.dart` — БД с уникальным именем на каждый target,
клонируется из шаблона `tentura_test_tpl_<fingerprint миграций>`.

### Что сделать

1. Сделать `_isMeritRankSuite()` устойчивым к бандлам: учитывать теги
   текущего теста/группы (`liveTest.test.metadata.tags`), а не только suite.
   Покрыть тестом: `mr`-файл внутри бандла берёт лок.
2. Разрешить бандлинг pg-файлов в `gen_test_bundles.py` под отдельным флагом
   (например `--allow-pg`), чтобы локальное поведение по умолчанию не
   менялось. Никогда не бандлить:
   - файлы с тегом `mr` (в CI pg-прогоне они и так исключены, но генератор
     не должен полагаться на фильтр снаружи);
   - файлы с `multi-connection` (они меряют латентность/RSS под нагрузкой и
     идут `-j 1`);
   - файлы, которые сами задают размер пула или трогают процессные
     синглтоны / `Platform.environment` так, что это видно следующему файлу.
3. Найти утечки между файлами в одном изоляте и чинить их или вносить файл в
   `packages/server/test/bundle_exclude.txt` с комментарием-причиной.
   Типичные: незакрытые `Connection` / `TenturaDb` (при pool size 1 и
   `max_connections` Postgres накапливаются), висящие `Timer`/подписки, GetIt,
   статические кэши, переопределения Env. Генератор уже добавляет
   `_resetBetweenFiles` (GetIt) — проверить, достаточно ли этого для server.
4. Подключить бандлы в CI-ветке `pg)` (`pipeline.yml`): шард файлов →
   `gen_test_bundles.py . --allow-pg --chunks K <файлы шарда>` → `dart test`
   с теми же флагами (`TENTURA_TEST_PG_POOL_SIZE=1`, `--tags pg --exclude-tags
   mr,multi-connection`). Подобрать K и `-j` по замерам (pg CPU-bound: `-j 4`
   против `-j 2` давал лишь +15%).
5. Если задача 2 уже ввела балансировку по длительности, бандлы строить
   **после** выбора файлов шарда, чтобы баланс не ломался.
6. Локальный профиль `server-pg` в `scripts/run_tests.sh` не трогать:
   per-file прогон остаётся эталоном. Перевод локального профиля на бандлы —
   отдельное предложение с замерами, не часть задачи.

### Критерии приёмки

- Число тестов в pg-выборке совпадает с базой (per-file против бандлов, тот
  же коммит, один шард и полный набор).
- 5 подряд зелёных `ci:full`-прогонов без новых флейков; любой флейк,
  появившийся только в бандле, — либо фикс изоляции, либо файл в
  `bundle_exclude.txt` с причиной.
- Тест из пункта 1 есть и проходит.
- Шаг тестов pg-шарда короче минимум на 30% против замера после задачи 2 (или
  против базы, если задача 2 ещё не сделана). Если выигрыш меньше 15% — задачу
  остановить, отчитаться цифрами и не мержить.
