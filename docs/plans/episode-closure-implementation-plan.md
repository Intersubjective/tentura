# Закрытие эпизода и обновление доверия — план реализации

**Status:** draft, rev 9. Ждёт утверждения.

**Дата:** 2026-09-28

**Основание:** `post-request-closure-social-design.md` (rev 3, D1–D22, §17.4). Здесь не пересказывается, почему устроено именно так; этот план — как построить.

**Связанные:** `subjective-help-tag-evidence-architecture.md` (close-ack как outcome evidence, D16/D19) · `~/MY_SRC/meritrank-rust/NEGATIVE_EDGES_FEATURE.md` (реализовано в service v0.11.0 / core 0.12.0) · `received-reviews-trust-changes-plan.md` (#107 — отменяется целиком этим планом).

**Рамки выкатки:** пользователей нет, только тестеры; клиент только web. Старая совместимость не строится: одна выкатка, после неё поднимается `kDefaultMinClientVersion`. Старые данные отзывов и доверия удаляются.

## 0. Резюме

Три фазы.

- **Фаза 0 (срочно, отдельный PR).** Tentura уже на MR v0.11.0, где отрицательный вес — это стена, а TT до сих пор публикует знаковый `trust_edge_weight`. Каждый плохой отзыв сейчас стоит стеной (при λ=0 стена только не начисляет доверие). Нужно обрезать вес до ≥0 и заново опубликовать все рёбра.
- **Фаза A — новое закрытие.**
  - Пятибалльный отзыв о людях удаляется целиком.
  - Автор отмечает исход по каждому принятому офферу, делает личные «спасибо» с запиской и пишет рассказ.
  - Помощники в это же время могут закрыто отметить вклад коллег слайдерами (беспристрастный делёж плюс своё ребро, V3).
  - Доверие собирается из корзин по типам событий, а не из знаковых корзин валентности.
- **Фаза B — стены.**
  - Бан публикуется как −1.
  - Появляется стена «ты шумишь» из неразрешённых форвардов.
  - Сторона «я его дёргал» становится множителем при показе.
  - Добавляются барьер `mr_sync` и бутстрап стен.
  - λ остаётся 0 до симуляции.

Фаза C (переприглашение с поправкой на ранжирование, σ, тревога поручителю, заявление о несоответствии, наследование стен) и защита чтения от утечек в этот план не входят (§12).

## 1. Принятые решения

### 1.1 UX закрытия (решения владельца, 2026-09-28)

| # | Решение |
|---|---|
| **U1** | Личных чатов в Tentura нет. Текст конкретному человеку существует только как **записка к личному «спасибо»** автора |
| **U2** | Поверхности «спасибо»: (а) экран «Мне сказали спасибо» — все благодарности пользователю по всем запросам, виден только владельцу; (б) событие в запросе, видимое только получателю |
| **U3** | Голосовать можно за **любого одобренного на участие** помощника, включая тех, чей вклад автор не подтвердил. Бывшие помощники (ушёл или исключён) не участвуют |
| **U4** | Переход в состояние оценки (`BeaconStatus.reviewOpen`) открывает сразу два процесса: автор отмечает исходы, помощники по желанию отмечают вклад коллег |
| **U5** | Дедлайн оценки и авто-закрытие работают как сейчас: 7 дней, продления, sweep по истечении. Исход, на который автор не ответил, при авто-закрытии считается `noBasis` |
| **U6** | Если автор не начал закрытие, помощник может у себя отправить запрос в архив. Эффекта на доверие нет, это только скрытие из списков |
| **U7** | Автору **раз в неделю** приходит напоминание о «протухшем» запросе. Протухший = статус из открытой семьи и (срок `end_at` прошёл **или** N дней без активности) |
| **U8** | ~~Слайдеры «передать часть своей доли» с остатком «себе»~~ — **заменено U21**. Шаг 5% и видимость получателю сохраняются |
| **U9** | Экран слайдеров видят **все** одобренные помощники: в момент выбора никто не знает, что решит автор |
| **U10** | Личное «спасибо» — получатель видит **только факт и записку**, без величины (и от автора, и от коллеги) |
| **U11** | Ребро H→F («мне прислали стоящее») ставится **автоматически** при одобрении оффера и **снимается**, когда помощник ушёл или исключён |
| **U12** | Переоткрытие отменяет всё. Введённые данные (исходы, спасибо, записки, рассказ, слайдеры) **сохраняются и предзаполняются** при следующем закрытии |
| **U13** | Рассказ о закрытии **опционален** |
| **U14** | Бюджет эпизода **фиксирован** (Q1 = вариант а). Если никто не подтверждён, помощникам ничего не чеканится |
| **U15** | Цепочке платят за одобренного помощника, независимо от исхода (Q2 закрыт решением §11 записки) |
| **U16** | Доверие строится из **корзин по типам событий** («помог», «полезный форвард», «спасибо», «шумел», …). У каждой корзины своё затухание и насыщение; корзины смешиваются с весами и сворачиваются в ребро. Категориальная шкала валентности уходит |
| **U17** | Утечки на стороне чтения (`graph()` с `positive_only` от клиента, `graph_edges_between`, оракулы) **в этом плане не чинятся** |
| **U18** | Напоминание о протухшем запросе шлётся автору **даже если помощников никогда не было** |
| **U19** | Вовлечение в форвард = оффер на этот запрос, форвард дальше или перевод в Watching. «Не могу помочь» нейтрально |
| **U20** | На экране голосования за кнопкой (i) — **визуальная схема** с реальными аватарами: благодарность идёт от автора, помощник не дарит и не теряет своё, а влияет на то, как делится благодарность автора (A11) |
| **U21** | ~~V3: голос одновременно двигает пул и ставит своё ребро~~ — **заменено U24**: голос только делит, рёбер не ставит |
| **U22** | ~~Двое: обязательная уступка через голос~~ — **поглощено U24**: при двоих голоса нет, остаётся только спасибо из своей доли (оно и есть уступка) |
| **U23** | Ферма ссылок в MR не работает: попадания дедуплицируются внутри забега. Ограничение проверяется как **доля сдвига рамки**, а не как «эмиссия» |
| **U24** | **Два независимых слоя.** (1) **Честный делёж** — слайдеры голоса (при `|M| ≥ 3`), беспристрастные, **рёбер не ставят**. (2) **Спасибо от себя** — и у автора, и у помощников. Только оно ставит **личное ребро** (корзина `thanks`) — это отношение. Привязать личное ребро к честному дележу нельзя: это превращает делёж в ритуал «всем поровну, все друзья» |
| **U25** | **Спасибо — галочка фиксированного размера: 10% пула автора** (`u = 0.1·pool_h`), «или ничего, или 10%». Автор — не больше трёх, из пула до дележа. Помощник — из своей доли после дележа, в сумме не больше доли (перебор уменьшается пропорционально) |
| **U26** | **Сальдо — только для авторской массы.** Встречные спасибо взаимно гасятся в рамке автора, но **личные рёбра ставятся по каждому спасибо**, включая взаимные и круговые. Взаимные рёбра скрепляют личные связи. Циклы разрешены; их обработка (разбиение, ослабление) — отдельный уровень алгоритма над свидетельствами, не в правилах выбора (§12) |
| **U27** | Цена спасибо — в абсолюте: 10% пула значат много для того, кому досталось мало, и немного для того, кому досталось много. Благодарность поэтому течёт в основном «сверху вниз» |
| **U28** | **Двое помощников: доли назначает автор.** Честного дележа для двоих нет, поэтому автор сам ставит соотношение (шаг 10%, по умолчанию поровну между подтверждёнными). Помощники могут только сказать друг другу спасибо, и оно стоит **30% своей назначенной доли** (а не 10% пула). Доля запечатана, поэтому цена остаётся неизвестной и дорогой. Исключение из D9/D12 записки (автор не сравнивает людей и не распоряжается долями) — осознанное и только для `|M| = 2`: сравнение видит один автор, котёл по-прежнему ненаблюдаем |
| **U29** | **Спасибо помощника — упорядоченный список до трёх человек.** Оплата идёт по порядку: каждому целиком `u` = 10% пула, пока хватает доли. Остаток меньше `u` переходит следующему и считается оплатой, если он ≥ `u/2`; иначе остаётся у дающего. Дробных спасибо нет. Пропорционального урезания больше нет: оно делало лишнюю галочку бесплатной («всем сёстрам по серьгам») |
| **U30** | **Ребро спасибо = оплата + предпочтение.** Оплата — реально перенесённая масса автора. Предпочтение — фиксированный личный бюджет `π` на эпизод, делится по рангу геометрически (`r = 0.5`, нормировка к сумме `π`: 1 · 2/3, 1/3 · 4/7, 2/7, 1/7). Неоплаченное спасибо ставит ребро только из предпочтения. Каждый следующий в списке ослабляет ребро первому — цена у галочки есть даже при нулевой доле |
| **U31** | **Записка:** к спасибо №1 доходит **всегда**; к №2 и №3 — только если спасибо оплачено. У каждого есть один гарантированный голос словами, а выбор, кому его отдать, уже дорог |
| **U32** | **Размер `u` фиксирован** (10%, не случайный). Помощник может грубо узнать свою долю по итогу доставки — это знание о себе; требование §15 записки — ненаблюдаемость котла для других, и оно сохраняется |
| **U33** | **Ранг и оплата получателю не видны никогда.** Получатель видит только «X лично поблагодарил тебя» (+ записка, если доставлена). Дающий после закрытия видит мягкий итог без чисел: «Маша и Петя получили твоё спасибо; для Димы твоё отношение учтено, записка не дошла». В интерфейсе нет слова «оплата»: спасибо «усиливается» твоей частью благодарности |

### 1.2 Решения этого плана (предлагаются, требуют утверждения)

| # | Решение | Альтернатива |
|---|---|---|
| **P1** | **Доли — на исходящих рёбрах автора; личные рёбра — только из спасибо.** Доля j — это `author→j` (`helped`). Голос двигает часть пула автора и ничего больше. Спасибо i→j перекладывает `u` авторской массы с `author→i` на `author→j` (встречные гасятся в сальдо) и ставит `i→j` (`thanks`) размером `u` | привязать ребро к голосу — ритуал |
| **P2** | **Шага «отправить пакет» нет.** Всё, что сохранено к моменту финализации, учитывается. Черновик и есть ответ | оставить «Send», как сейчас — возвращает ритуал |
| **P3** | **«Завершить сейчас»** доступно автору, когда он ответил по всем офферам **и** (все помощники нажали «готово» **или** с открытия прошло ≥ 48 ч). Иначе автор мог бы закрыть мгновенно и отнять у помощников перераспределение (D11) | закрытие в любой момент |
| **P4** | Решения автора **запечатаны до финализации**. Помощник видит свой исход и полученные голоса только после закрытия | — |
| **P5** | **Help-tag close-ack.** Подтверждённый оффер порождает close-ack автора на заявленные в оффере `helpTypes` (D16 help-tag, финализация). Взаимные close-ack помощников исчезают вместе с формой отзыва | отдельный выбор тегов на экране автора |
| **P6** | **Поручительство (`vote_user`) — состояние, а не свидетельство.** Корзина `vouch` читается из текущего `vote_user` при пересборке (голос > 0 даёт вклад, ≤ 0 не даёт) и не затухает. Приглашение создаёт взаимные `vote_user` | оставить затухание 182 дня, как сейчас |
| **P7** | Свидетельства хранятся **в журнале с отзывом** (`retracted_at`), корзины пересчитываются **из журнала** при каждой пересборке пары. Инкрементального аккумулятора с anchor-инфляцией больше нет: обратимость бесплатна (U11, U12) | аккумулятор + компенсирующие записи |
| **P8** | **Рассказ** — системное сообщение комнаты (kind 3 `closureStory`), видно всем, кто читает комнату. **Персональные итоги** (исход, голоса, спасибо) — per-viewer запрос плюс receipt в outbox. В комнате нет адресации одному получателю, и новый столбец видимости ради этого не заводится | столбец `recipient_id` у `beacon_room_message` |
| **P9** | Второй путь «переоткрытия» (`reviewOpen → needsMoreHelp` в `CoordinationCase.setBeaconStatus`) сводится к той же операции reopen | — |
| **P10** | После финализации переоткрыть запрос нельзя, как и сейчас (`kMaxReviewReopens = 1`, только из окна оценки) | — |
| **P11** | **Форвардный движок сохраняется** как алгоритм потока 1 (§4.1): DAG → обратное распространение массы с атрибуцией → нормировка по отправителю → бюджет на отправителя. Меняются только вход (одобренные помощники вместо оценок автора) и выход (корзина `routed` на рёбрах `отправитель→получатель`). Удаляются знаковые ветки (`negativeRoute`, `unsuccessfulRequestForward`) | геометрия назад с фиксированной суммой (записка §11) |

## 2. Факты о текущем коде, на которых стоит план

Сокращения: **M** = `packages/server/lib/data/database/migration/m0193.dart` (сквош-бейзлайн), **S** = `packages/server/lib/`, **C** = `packages/client/lib/`.

**Доверие**

- Цепочка записи: `TrustEvidenceRepository.record` (S/data/repository/trust_evidence_repository.dart:22) → `trust_evidence_event` (M:5833) → `trust_apply_source_evidence` (M:4138), аккумулятор с anchor-инфляцией → `trust_rebuild_effective_edge` (M:4256) → `mr_put_edge`, если вес изменился больше чем на ε=0.1.
- `trust_edge_weight` (M:4205) = `(−5vb − b + g + 5vg)/(5 + Σ)` — знаковый. Бан публикует **0**, и только если строка пары уже есть (M:4304).
- `TrustSourceType` содержит 5 членов, `TrustContext` — personal/commitment/forward (+legacy), `trust_context_config`: forward ×0.2. Период полураспада один глобальный — 182 дня (`trust_policy`).
- **Пути отзыва нет** (кроме capability-событий).
- `mr_sync` нигде не вызывается. Postgres-образ `postgres-tentura:v0.8.0` = pgmer2 0.8.0, без барьера 0.8.1.
- `meritrank_init()` (M:2138) грузит `user_trust_edge.prev_sent_weight` и polling-рёбра.
- Писатели свидетельств:
  - голос / подписка / отписка (`user_trust_edge_repository.dart:138-185`, bin×3);
  - приглашение (`user_repository.dart:937`, взаимно good×3);
  - финализация отзывов (`review_finalization_case.dart:133-316`: `finalizedRequestEvaluation`, форвардный движок, `unsuccessfulRequestForward`).
- Форвардный движок: S/domain/trust/forward/* — `ForwardCausalGraphBuilder` (рёбра до момента оффера, цепочка к автору), `ForwardMassPropagator` (масса 1 от коммиттера назад: у коммиттера поровну по отправителям, выше — по `forward_decision_attribution`), `ForwardLocalNormalizer`, `ForwardRequestConsolidator` (бюджет 1.0 на отправителя за запрос). Пишет на рёбра **отправитель → получатель** каждого звена. Сохраняется (P11).
- Поддержание: `TrustMaintenanceCase` — sweep раз в 24 ч, партии по 200.

**Закрытие**

- Статусы: `BeaconStatus` open(0), cancelled(1), deleted(2), draft(3), reviewOpen(5), closed(6), needsMoreHelp(7), enoughHelp(8). Открытая семья — {0, 7, 8}.
- `EvaluationCase.beaconClose` (S/domain/use_case/evaluation_case.dart:163):
  - если коммиттеров никогда не было → сразу `closed`;
  - иначе → `reviewOpen` с окном 7 дней (`_reviewWindowDuration`), участниками, видимостью и статусами пакетов.
- Продление: +7 дней, максимум 2. Close-now требует, чтобы все обязательные пакеты были отправлены. Reopen только из открытого окна, `kMaxReviewReopens = 1`.
- Авто-закрытие: `AttentionExpirySweepCase` раз в минуту в `TaskWorkerCase`.
- Таблицы `beacon_evaluation*`, `beacon_review_status`, `beacon_review_window` (M:4988-5283). Роли: author, committer, forwarder, formerCommitter; `EvaluationParticipantGraphBuilder`.
- Путь прихода помощника: `fetchHelpOffererPathChain` (S/data/repository/forward_edge_repository.dart ~175). Форварды: `beacon_forward_edge` (sender, recipient, parent_edge_id, cancelled_at, recipient_rejected, recipient_read_at).
- Одобрение оффера и выход помощника: `CoordinationCase` accept / decline / remove / release (coordination_case.dart:324-492), `HelpOfferCase.withdraw`. `beacon_commitment_event` kinds 0–8.

#### 3.2.1 Назначение корзин и смешивание

Корзина — это **одна причина доверять**, у которой своя память и свой потолок. Корзины не взаимозаменяемы: сколько ни накопи в одной, её вклад ограничен её весом `mix`. Поэтому дешёвый в фарме тип события не может заменить дорогой.

Три ручки на корзину:

- **hl — память.** Каждое событие затухает вдвое за `hl`. Без подкрепления сигнал уходит сам (D5): это единственная санкция за прекращение.
- **k — насыщение.** Вклад корзины равен `s/(k+s)`: при `s = k` корзина даёт половину потолка, дальше отдача убывает. Повторять одно и то же с одной парой почти бесполезно (глубина ограничена).
- **mix — потолок и вес.** Максимальный вклад корзины в ребро. `T = Σ mix·s/(k+s)` лежит в `[0, Σ mix)`.

Абсолютная величина `T` почти не важна: MR нормирует исходящие рёбра каждого субъекта. Важно, как рёбра одного человека соотносятся между собой.

Пример при стартовых параметрах. В эпизоде автор A подтвердил двух помощников, B = 1, ρ = 0.3, так что доля каждого 0.35.
- `helped` у H: `1.0 · 0.35/1.35 ≈ 0.26`.
- Плюс личное «спасибо»: `0.5 · 0.3/0.8 ≈ 0.19`. Итого ≈ 0.45.
- Для сравнения, подписка (vouch) = `1.0 · 1/2 = 0.5`.
- Три таких эпизода подряд дают `helped ≈ 0.51`, десять — ≈ 0.78, и никогда не больше 1.0.
- Через год без новых эпизодов `helped` падает примерно вдвое.



```
s_k   = Σ_{live rows of kind k} count · 2^(−age/hl_k)     (hl NULL → без затухания)
T     = Σ_{k: trust} mix_k · s_k / (k_k + s_k)            (vouch: s = 1, если голос > 0)
n     = s_noisy
wall  = 1                    если user_block(subject → object)
      = level(n)             иначе, если T = 0 и n ≥ θ    (level — квантованный уровень < 1)
      = 0                    иначе
target = −1        если бан
       = T         если T > 0
       = −wall     если wall > 0
       = 0
```

Смысл: бан сильнее всего, доверие сильнее «шумит» (§17.4 записки), стена «шумит» публикуется только на незнакомца. В фазе A есть только ветки «бан → 0» (как сейчас) и T. Ветка стены и «бан → −1» включаются в фазе B.

**Правило публикации:** публикуем, если `|target − prev| > ε` **или** сменился знак **или** сменился квантованный уровень стены.

n = |M|
μ_eff = μ, если n ≥ 3, иначе 0

### 4.2 Два слоя: честный делёж и спасибо от себя (U24)

**Почему два слоя.** Беспристрастный делёж ценен тем, что голос ничего не стоит голосующему. Именно поэтому к нему нельзя привязать личное ребро: бесплатное ребро за голос превращается в ритуал «всем поровну, все друг другу друзья». Личное ребро выражает отношение, а отношение достоверно, только когда стоит тому, кто его выражает. Поэтому это разные действия с разными свойствами.

| | Слой 1: честный делёж | Слой 2: спасибо от себя |
|---|---|---|
| Вопрос | «Кто, по-твоему, сделал больше?» | «Кого хочешь поблагодарить от себя?» |
| Кто | помощники, при `|M| ≥ 3` | автор и помощники |
| Откуда масса | срез пула автора `μ·pool_d/n` | автор — `u = 10%` пула за каждое (≤ 3), до дележа; помощник — до трёх по порядку, оплата целыми `u` из своей доли после дележа, плюс бюджет предпочтения `π` |
| Стоит ли дающему | нет (беспристрастно) | да |
| Личное ребро | **нет** | **да**, `thanks` |
| Записка | нет | да, до 280 символов |
| Видит получатель | «X отметил твой вклад: 40%» | «X лично поблагодарил тебя» + записка, если доставлена (U31); ранг и оплата не видны (U33) |

**Слой 1 — честный делёж.** Каждый помощник делит свой срез пула автора только между **другими**. Доля j зависит от решения автора и голосов других, но не от голоса самого j. Это простейший беспристрастный делёж (partition rule, в духе de Clippel–Moulin–Tideman 2008). Консенсусное свойство точной формулы dCMT (единогласные отчёты воспроизводятся точно) он не даёт. Кто не голосовал, чей срез идёт поровну подтверждённым. `μ` — доля пула, открытая голосам (стартово 0.5).

**Слой 2 — спасибо от себя.** Галочка фиксированного размера `u = 10%` пула автора: или ничего, или 10% (U25). Решение принимается одновременно с голосованием, в одном окне, без второй фазы:
- доля до финализации запечатана (P4), поэтому котёл остаётся ненаблюдаемым (записка §15);
- цена спасибо в абсолюте (U27): одни и те же 10% — большая часть скромной доли и малая часть большой. Благодарность поэтому течёт в основном «сверху вниз», от тех, кому досталось больше, к тем, кому меньше. Это выравнивает делёж автора и работает против Матфея: рёбра «снизу вверх» появляются реже;
- порядок и оплата (U29): до трёх человек; оплата идёт целыми 10% по порядку, пока хватает доли, остаток ≥ 5% достаётся следующему. Пропорционального урезания нет: при нём лишняя галочка ничего не стоила бы;
- ребро = оплата + предпочтение (U30). Бюджет предпочтения `π` фиксирован и делится по рангу, поэтому каждый следующий в списке ослабляет ребро первому. Пример: доля 18%, порядок Петя, Маша, Дима → Петя 10% + 5,7%, записка; Маша 8% + 2,9%, записка; Дима 0 + 1,4%, без записки. Если бы в списке был один Петя, его ребро было бы 20%;
- записка (U31): к первому спасибо доходит всегда, к остальным — если оплачено. Слово «оплата» в интерфейсе не используется: спасибо «усиливается» твоей частью;
- если автор не подтвердил дающего и никто не отдал ему голос, `share = 0`: масса не переносится, рёбра — только из предпочтения, записка — только первому.

Спасибо **автора** — те же галочки по 10% из пула эпизода до дележа, не больше трёх.

**Малые группы.**

| `|M|` | Слой 1 | Слой 2 |
|---|---|---|
| 1 | нет | только спасибо автора |
| **2** | нет: делёж для двоих вырождается. **Доли назначает автор** (U28), шаг 10% | спасибо = оплата **30% своей назначенной доли** + предпочтение `π`; записка доходит всегда. Доля запечатана, поэтому цена неизвестна и дорога. Взаимное гасится в массе частично: при разных долях сальдо идёт от того, кому автор дал больше. Даёт два ребра |
| ≥ 3 | да | да |

**Роль автора.**
- Решает, кто подтверждён (C). Это задаёт равную часть пула, направление срезов промолчавших и, через `share`, размер того, из чего помощники могут благодарить.
- Благодарит из пула (слой 0).
- Не видит голосов и спасибо помощников и не утверждает их (D11).
- Не меняет `μ`.
- Если автор не подтвердил никого, эпизод не состоялся: ни дележа, ни спасибо (U14).
- Направить срез или спасибо неподтверждённому — право коллег. Это единственная точка, где они могут частично не согласиться с автором.

### 4.3 Сальдо и циклы

- **Авторская масса** переносится аддитивно, поэтому встречные спасибо гасятся в ней сами: `final` считается по сальдо. Взаимное «спасибо ↔ спасибо» при равных `g` оставляет доли как есть.
- **Личные рёбра** ставятся по каждому спасибо валово, включая взаимные и круговые (U26). Правила выбора производят свидетельства и им не препятствуют.
- **Циклы.** Их обработка — разбиение, ослабление, учёт взаимности — отдельный уровень алгоритма, который работает над журналом свидетельств (например, как множитель при свёртке корзины `thanks` для пар и циклов). Это вне этого плана (§12). Здесь только требование к данным: в `metadata` строки `thanks` пишутся `closure_epoch`, `rank`, `paid` (оплачено ли) и `reciprocated` (было ли встречное в том же эпизоде). Это id-only, без содержания, и позволит построить тот уровень без миграции журнала.

### 4.1 Поток 1: обратное распространение по цепочке (движок сохраняется)

Что делает движок сейчас:
- Для каждого коммиттера строит DAG форвардов, созданных до его оффера и не отменённых, с корнем у автора.
- Пускает массу 1.0 назад от коммиттера. У самого коммиттера она делится поровну между теми, кто ему переслал. Выше по цепочке — по весам `forward_decision_attribution` («я переслал, потому что получил от X»), иначе поровну.
- Нормирует массу внутри каждого отправителя и складывает по коммиттерам.
- Выдаёт каждому отправителю бюджет 1.0 на запрос, распределённый по его получателям пропорционально их вкладу.
- Пишет свидетельство на ребро **отправитель → получатель**: «моё решение переслать сюда сработало».

Что меняется:

| | Сейчас | Становится |
|---|---|---|
| Кто запускает массу | коммиттеры, которых автор оценил; значение оценки → bin | **все члены эпохи M** (одобрен и не ушёл), с массой 1.0 каждый; исход не важен (U15, I4) |
| Бюджет на отправителя | 1.0 за запрос | **ρ·B** за эпизод (параметр) |
| Выход | bins good/veryGood/noEffect в контексте forward ×0.2 | корзина `routed`, count = доля бюджета |
| Неудачные форварды | `unsuccessfulRequestForward` (noEffect) | **удаляется** — неудача = отсутствие платежа (записка §16) |
| `negativeRoute` | noEffect-провенанс для оценок 1–2 | **удаляется** — знаковой шкалы больше нет |
| Идемпотентность | `hasForwardEvidenceForRequest` | `source_key` с эпохой + отзыв эпохи при reopen |

Почему бюджет на отправителя, а не фиксированная сумма на эпизод (как в записке §11). Паддинг цепочки сибилами создаёт массу только на рёбрах самих сибилов. Масса в честной рамке — например, `F→S1` у честного форвардера F — ограничена бюджетом F. Прибыль кольца ограничена attack edges, как и должно быть. Фиксированная сумма на эпизод ограничивала бы то же самое, но ценой того, что длинная честная цепочка платит каждому звену меньше.

Сочетание с корзинами. Поток 1 — это просто ещё один писатель корзины `routed`. Повторные успешные маршруты `F→R` в разных эпизодах накапливаются и насыщаются (k = 1): это и есть «F знает, куда слать». Затухание 182 д. Тот же `F→R` может одновременно нести `vouch`, если F подписан на R: корзины складываются через свёртку, каждая со своим потолком. Потоки 1 и 2 направлены противоположно и не дублируются. Поток 1 — `F→H`: «правильно, что я переслал H». Поток 2 — `H→F`: «F прислал мне стоящее».

Переименование: `ForwardOutcomeFinalizer` → `ForwardRoutingSettlement`. `forward_outcome_policy.dart` удаляется. `TrustBin`/`TrustSourceType` в движке заменяются на `TrustEvidenceKind.routed`. Юнит-тесты движка (`forward_outcome_finalizer_test`, `forward_request_consolidator_test`) переносятся с новым входом; удаляются только ветки negativeRoute и unsuccessful.

## 5. Жизненный цикл закрытия

```
open family ──close──▶ reviewOpen (epoch e, status 0)
   │                     │  автор: outcomes / thanks / story (черновики)
   │ (если коммиттеров   │  помощники: голоса, «готово»
   │  никогда не было)   ├──reopen──▶ open family   (epoch e → 2 cancelled; черновики живут)
   ▼                     ├──closeNow (P3)──┐
 closed                  └──closes_at < now (sweep)──┴──▶ finalize ──▶ closed (epoch e → 1)
```

**finalize** — одна транзакция под локом запроса:

1. Статус эпохи становится 1, `beacon.status = closed`, событие жизненного цикла.
2. Собрать вход, вызвать `EpisodeSettlement`.
3. Записать свидетельства в журнал (`ON CONFLICT (source_key) DO NOTHING`), затем пересобрать затронутые пары.
4. Записать close-ack capability-события (P5), в той же транзакции (help-tag §764).
5. Если рассказ непуст — системное сообщение комнаты `closureStory` (kind 3).
6. Outbox, по получателю: исход (каждому члену), голоса (каждому получателю), спасибо с запиской (каждому получателю).
7. Закрыть обязательства (supersede) — как сейчас.

**reopen**: эпоха получает status 2. Свидетельства эпохи отзываются (`retracted_at`), пары пересобираются. В фазе A это пустая операция, потому что до финализации свидетельств нет, но функция пишется общая. Статус возвращается в open, `review_reopen_count++`, отправляется receipt `closureCancelled`. Черновики не трогаются.

**Вход в эпоху (close):** снимок `beacon_closure_member` = текущие одобренные (`hasCurrentStake`) плюс `arrival_edge_id`. Receipt `closureOpened`: автору — «подведи итоги», помощникам — «можешь перераспределить (необязательно)».
