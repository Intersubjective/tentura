## 0. Резюме на одну страницу

Все семь симптомов из тикета — следствие **четырёх** независимых корневых причин, и только одна из них про UI-кнопки:

| # | Корень | Симптомы из тикета |
|---|--------|--------------------|
| **K1** | Раскладка не является отдельной фазой: алгоритм вшит в поток `GraphController._relayout()`, промежуточные итерации применяются покадрово, интерполяции нет | «expanded nodes jumped into unpredictable positions», «graph became difficult to read» |
| **K2** | Раскладка недетерминирована и **зависит от порядка раскрытия**: `existingLayout` как стартовая точка + `positionHint = _nodes.length` + накопление `pinned` + стохастика Fruchterman–Reingold | «The same graph state must not depend on the order in which nodes were expanded» |
| **K3** | Данные неполны по построению: `mr_graph(ego, focus, …, 0, 100)` отдаёт окрестность **только текущего фокуса**, а клиент никогда не запрашивает «рёбра между уже известными узлами» | «rendered a person without a visible path», «edges appeared only after navigating in the reverse direction» |
| **K4** | Взаимодействие перегружено: один тап = select + focus + fetch + pin, а «expand» — это невидимое правило «тапни ту же ноду ещё раз» | «users needed repeated/double clicks without knowing the interaction rule», «no obvious reset» |

Плюс архитектурное ограничение, которое блокирует нормальное решение K1/K2:

> **K5.** Библиотека не позволяет ни сменить алгоритм после `initState`, ни передать алгоритму семантику (кто ego, кто focus, какой путь активен, какой это вообще граф). Единственный канал влияния — поля `NodeBase`, отсюда и хак `positionHint`.

**Хорошая новость:** библиотека **уже форкнута** — `packages/force_directed_graphview` подключён через `pubspec_overrides.yaml`, в форке уже три собственных коммита (`5790036b`, `bb28bc93`, `ace838db`). Upstream `cupofme/force_directed_graphview` стоит на 0.6.2 и фактически не развивается. То есть вопрос не «можно ли форкать», а «сколько править». Вся библиотека — **1819 строк**, из них ядро (controller + view + FR-алгоритм) ≈ 700.

**Рекомендация:** план **B** (§7) — четыре точечных патча в форк (≈250 строк) + три детерминированных алгоритма раскладки на стороне приложения + серверный запрос «рёбра между известными узлами». Полная замена библиотеки (план D) не оправдана: рендер-слой у неё нормальный, проблема ровно в двух местах.

Плюс два самостоятельных куска работы по решениям владельца продукта, **не зависящих ни от форка, ни от сервера** и потому пригодных к параллельному исполнению:

- **§4-bis** — взаимное доверие как двухпутная дорога с левосторонним движением. Два встречных ребра **уже создаются и уже рисуются**, просто по одной и той же прямой, поэтому шейдеры накладываются; нужно развести их в стороны.
- **§5-bis** — фильтр негативных связей переезжает в легенду и становится «слоем карты»; попутно чинится то, что сейчас на телефоне этот фильтр недоступен вообще.

## 1. Карта того, что есть сейчас

### 1.1 Три графа — один код

Все три экрана используют **один** `GraphCubit` (957 строк) и **один** `GraphBody`:

| Экран | Точка входа | Источник | Режим `GraphCubit` |
|-------|-------------|----------|--------------------|
| Доверие / «Показать связи» | `GraphScreen` (`profile_body.dart:62`, `profile_view_body.dart:218`) | `GraphRepository` → Hasura `graph()` → `mr_graph` | по умолчанию |
| Форварды запроса | `ForwardsGraphScreen` | `ForwardsGraphRepository` → V2 `beaconForwardGraph` / `beaconHelpOffererForwardPath` | `forwardsGraphBeaconId != null` |
| Генеалогия приглашений | `InviteGenealogyScreen` | `InviteGenealogyRepository` | `genealogyMode: true` |

Различия зашиты внутрь кубита флагами: `_usesFocusPathVisibility`, `_focusRootId`, `_alwaysVisibleNodeIds`, `genealogyMode`, ветвления в `_fetch()` на ~140 строк. Легенда (#85) уже разведена через `GraphLegendMode { trust, forwards, genealogy }` — **это единственное место, где три графа уже честно разделены**.

### 1.2 Геометрия у трёх графов принципиально разная

| | Топология | Что означает направление | Что должна показывать раскладка |
|---|---|---|---|
| **Генеалогия** | лес/DAG, у узла ровно один родитель | пригласивший → приглашённый | строгие уровни сверху вниз, поколение = слой; ветви ego и target не перемешиваются |
| **Форварды** | DAG-цепочки от автора | переслал → получил | слои по хопам от автора; активная цепочка «автор → … → помощник» как хребет |
| **Доверие** | направленный граф **с циклами**, взаимные рёбра = две строки | subject доверяет object | концентрические кольца по расстоянию от ego; взаимность — визуальный признак ребра, а не геометрия |

Сейчас на все три натравлен **Fruchterman–Reingold** — алгоритм для неориентированных графов, который по определению игнорирует и направление, и иерархию, и семантику фокуса. Требование тикета «prefer directional/layered placement for the active traversal while supporting cycles» напрямую противоречит выбранному алгоритму.

### 1.3 Как устроен рендер-цикл библиотеки

```
GraphCubit.mutate(...)                       // добавили/убрали узлы и рёбра
  └─ GraphController._relayout()             // controller.dart:156
       └─ algorithm.relayout(existingLayout, nodes, edges, size)   → Stream<GraphLayout>
            └─ await for (layout) { _layout = layout; notifyListeners(); }
                 ├─ NodesView   (AnimatedBuilder → CustomMultiChildLayout)
                 ├─ LabelsView  (то же)
                 └─ EdgesView   (CustomPaint, repaint: controller)
```

`GraphLayout` — иммутабельная `Map<NodeBase, Offset>`. Позиция узла читается ровно в трёх местах: `_NodesLayoutDelegate.performLayout`, `_LabelsLayoutDelegate.performLayout`, `_EdgesPainter.paint`. **Это важно: одна точка внедрения интерполяции покрывает весь рендер.**

## 2. K1 — «нет фазы раскладки»

### 2.1 Что происходит

`graph_body.dart:27-33`:

```dart
layoutAlgorithm: const FruchtermanReingoldAlgorithm(
  initialPositionExtractor: initialPositionExtractor,
  iterations: kIsWeb && !kIsWasm ? 300 : 500,
  optimalDistance: 100,
  showIterations: true,     // ← вот здесь
  temperature: 500,
),
```

`showIterations: true` заставляет `_run()` делать `yield layoutBuilder.build()` **на каждой итерации**, а между итерациями стоит `await Future.delayed(Duration.zero)`. Значит:

- контроллер получает 300–500 разных раскладок подряд и на каждой зовёт `notifyListeners()`;
- `NodesView`/`LabelsView` пересобирают `CustomMultiChildLayout` со всеми узлами 300–500 раз;
- пользователь видит физическую симуляцию: узлы разлетаются, притягиваются, дрожат и оседают там, куда их занесло.

Это и есть «expanded nodes jumped into unpredictable positions». Формально это анимация, но анимация **процесса поиска решения**, а не перехода между двумя состояниями. Осмысленной траектории у неё нет.

### 2.2 Почему нельзя просто поставить `showIterations: false`

Можно, и это на порядок улучшит производительность (см. план A), но:

1. Узлы будут **телепортироваться** из старых позиций в новые одним кадром. Для 3–5 узлов это ещё читается, для 30 — теряется соответствие «кто куда уехал».
2. Новые узлы до завершения раскладки **не имеют позиции вообще** — `getVisibleNodes()` фильтрует по `layout.hasPosition` (controller.dart:55-72). То есть при `showIterations: false` раскрытие ноды выглядит как «полсекунды ничего, потом всё разом перепрыгнуло».

### 2.3 Чего не хватает в библиотеке

Ровно того, о чём пишет заказчик: **посчитать целевую раскладку целиком, а потом переехать к ней управляемым переходом**. В API нет:

- разделения «целевая раскладка» / «отображаемая раскладка»;
- какой-либо интерполяции между двумя `GraphLayout`;
- сигнала «раскладка завершена» (стрим просто закрывается, наблюдать это извне нельзя).

`GraphLayout` иммутабелен и держит `Map<NodeBase, Offset>` — интерполяция между двумя такими картами тривиальна (`Offset.lerp` по объединению ключей, для новых узлов — старт из позиции «родителя» или из центра). Патч **P2** в §6.

## 3. K2 — раскладка зависит от порядка раскрытия

Четыре независимых источника зависимости от истории. Каждый сам по себе ломает требование «The same graph state must not depend on the order in which nodes were expanded».

### 3.1 `existingLayout` как стартовая точка

`fruchterman_reingold_algorithm.dart:95-101`:

```dart
for (final node in nodesSnapshot) {
  layoutBuilder.setNodePosition(
    node,
    existingLayout?.getPositionOrNull(node) ?? initialPositionExtractor(node, size),
  );
}
```

и `relayout` крутит всего `iterations * 0.1` шагов (30–50). То есть новая раскладка — это **дошлифовка предыдущей**. Два разных порядка раскрытия дают две разные предыдущие раскладки и, следовательно, два разных результата. Это by design для force-directed (иначе граф «взрывался» бы при каждом добавлении), но для нас это прямой конфликт с требованием.

### 3.2 `positionHint = _nodes.length`

`graph_cubit.dart:477`, `:481`, `:591`, `:612` — начальная подсказка позиции равна **размеру словаря узлов на момент вставки**. То есть буквально «порядковый номер, в котором узел был впервые загружен». `initial_position_extractor.dart` раскладывает по этому номеру в сетку 5 строк × N колонок.

Раскрой A→B→C и получишь одни hint'ы; раскрой A→C→B — другие; раскрой то же самое, но с другой страницы (в `_fetch` порядок обхода `Set<EdgeDirected>` не гарантирован) — третьи.

Дополнительно `positionHint` входит в `NodeDetails.hashCode`/`==` (node_details.dart:36-54). А `GraphLayout._nodePositions` — это `Map<NodeBase, Offset>` с ключом по значению. Значит **`copyWithPositionHint()` меняет идентичность узла и обнуляет его позицию** в раскладке. `copyWithPinned` в `==` не входит, поэтому пиннинг позицию сохраняет, а смена hint'а — нет. Это скрытая мина.

### 3.3 Накопление `pinned`

`setFocus` → `_pinNode` (`graph_cubit.dart:203-213`) пиннит каждую ноду, на которую пользователь когда-либо нажал, и никогда не отпинивает. В FR пиннованный узел (`_runIteration`, строка 201: `if (v.pinned) continue;`) **не смещается, но продолжает отталкивать других**. После 5–10 тапов половина графа зафиксирована в местах, куда её когда-то занесла симуляция, а остальные узлы вынуждены обтекать этот застывший каркас.

Это прямой ответ на «after exploration the graph became difficult to read».

### 3.4 Двойной relayout на один пользовательский тап

`setFocus` (строки 189-196) зовёт `_recomputeVisibility()` → `mutate()` → relayout №1. Затем, если фокус не был раскрыт ранее, вызывается `_fetch()`, который в конце зовёт `_updateGraph()` → `_recomputeVisibility()` → `mutate()` → relayout №2. Второй relayout стартует с результата первого (который сам не успел досчитаться и был отменён по `_relayoutGeneration`). Результат зависит от тайминга сети.

## 4. K3 — данные, а не картинка

Это единственная группа симптомов, которую **невозможно починить в клиенте**.

### 4.1 Что отдаёт сервер

`m0108.dart`:

```sql
CREATE OR REPLACE FUNCTION public.graph(focus text, context text, positive_only boolean, hasura_session json)
RETURNS SETOF public.graph_score AS $$
SELECT g.src, g.dst, g.score_cluster_of_ego, g.score_cluster_of_dst,
       user_trust_edge_degree(g.src, positive_only),
       user_trust_edge_degree(g.dst, positive_only)
FROM mr_graph(hasura_session->>'x-hasura-user-id', focus, context, positive_only, 0, 100) AS g;
$$;
```

Поверх этого `graph_fetch.graphql` накладывает `order_by: {dst_score: desc}, offset: $offset, limit: $limit`, а клиент (`graph_cubit.dart:465`) шлёт `offset` всегда 0 и наращивает `limit` на `kFetchWindowSize = 5` при каждом повторном тапе.

Отсюда три жёстких следствия:

1. **Окно 100 строк зашито в SQL.** Узел с более чем 100 инцидентными рёбрами не покажет остальные никогда, сколько ни листай.
2. **Возвращается окрестность фокуса, а не подграф на известных узлах.** Ребро A→B попадает в ответ, только если A или B — текущий фокус (и попало в топ-100 по `dst_score`). Пользователь раскрыл A, увидел B и C; ребра B→C ему никто не пришлёт, пока он не встанет на B или C. Это ровно «expected edges appeared only after navigating in the reverse direction».
3. **Ранжирование по `dst_score desc` при растущем `limit`** означает, что интересное пользователю ребро может лежать на 40-й позиции и появиться только после восьми повторных тапов.

### 4.2 Что клиент делает поверх этого

`_fetch` (строки 502-516) **явно добавляет ноду фокуса, даже если ни одно ребро её не содержит**:

```dart
// Add FocusNode in case there were no edges containing it
if (state.focus.isNotEmpty && !_nodes.containsKey(state.focus)) { … }
```

Это и есть «rendered a person without a visible path to the current focus» — узел на экране без единого ребра, буквально по коду.

Плюс `_recomputeVisibility()` (строки 871-956) держит в `visibleNodeIds` весь `_focusPathIds` **безусловно**, но рёбра между соседями по пути показывает только если они есть в `_allEdges`. Если ребро между двумя соседними шагами пути не было загружено — на экране висит разорванная цепочка узлов без соединений.

### 4.3 Решение: структура из Postgres, ранжирование из MeritRank

Ключевое наблюдение: **`user_trust_edge` — обычная таблица Postgres** (`m0088.dart`), с `PRIMARY KEY (subject, object)` и `prev_sent_weight`. Она уже используется для подсчёта степени узла (`user_trust_edge_degree`).

Значит структуру подграфа можно получать чистым SQL, не трогая MeritRank:

```sql
-- предлагаемое: graph_edges_between(node_ids text[], positive_only boolean)
SELECT subject AS src, object AS dst, prev_sent_weight AS weight
FROM public.user_trust_edge
WHERE subject = ANY(node_ids) AND object = ANY(node_ids)
  AND (positive_only = false OR prev_sent_weight > 0);
```

Разделение ответственностей становится честным:

- **MeritRank** отвечает на вопрос «кого показывать» (кто вообще релевантен, в каком порядке, с какими score) — существующий `graph()`;
- **Postgres** отвечает на вопрос «как показанные связаны» (замыкание рёбер на уже видимом множестве) — новый `graph_edges_between()`.

После каждого раскрытия клиент делает один добор `graph_edges_between(видимые_узлы)` и получает **гарантию**: у любой видимой пары, между которыми есть ребро, это ребро нарисовано. Требование «A rendered connection must have a consistent visible explanation/path» становится проверяемым инвариантом, а не надеждой.

Приватность: решение принято — показывать можно (§10.1), `can_read_content`-стены здесь нет, поведение наследуется от `mr_graph`.

## 4-bis. Направление доверия: двухпутная дорога с левосторонним движением

**Решение (§10.4):** направление уже передаётся бегущим по ребру шейдером, стрелки в графе доверия не нужны. Взаимное доверие рисуется как **два отдельных ребра**, каждое со своим шейдером, разведённые в стороны как пути двухпутной железной дороги (левостороннее движение). Односторонняя связь остаётся на центральной оси, как сейчас.

### 4-bis.1 Хорошая новость: два ребра уже есть в модели

`_allEdges` в кубите — это `Map<(String, String), EdgeDirected>` с ключом-парой, то есть A→B и B→A хранятся **раздельно**. `_recomputeVisibility` (`graph_cubit.dart:879-891`) явно кладёт в `visibleEdges` и `forward`, и `backward`, а `mutate` добавляет оба в контроллер. Библиотечный `_edges` — тоже `Set<E>`, а `EdgeDetails.==` учитывает `source`/`destination` по порядку.

**То есть оба ребра уже создаются и уже рисуются — просто по одной и той же прямой.** Два линейных градиента бегут навстречу друг другу по одному пикселю, накладываются и читаются как одна пульсирующая линия без внятного направления. Именно поэтому взаимность сейчас невидима.

Значит задача не «научиться рисовать два ребра», а «развести уже существующие два ребра в пространстве».

### 4-bis.2 Ключевое свойство: смещение считается локально

Каждое ребро смещается **влево относительно собственного направления движения**. Тогда встречное ребро автоматически окажется с другой стороны — и painter'у не нужно ничего знать о существовании парного ребра, кроме факта «связь взаимная».

В экранных координатах (ось Y вниз) левая нормаль к направлению `d = (dx, dy)`:

```dart
final n = Offset(d.dy, -d.dx) / d.distance;   // левая нормаль
```

Проверка: `d = (1, 0)` (движение вправо) → `n = (0, -1)` — вверх, то есть слева по ходу. Верно.

### 4-bis.3 Что менять — форк библиотеки НЕ требуется

`EdgePainter.paint(canvas, edge, srcPos, dstPos)` получает само ребро, а `EdgeDetails` — наш класс в приложении. Достаточно донести до painter'а один флаг:

```dart
// edge_details.dart
final bool isReciprocal;   // существует ли встречное ребро между теми же узлами
```

Заполняется в `_buildEdgeDetails` одной проверкой по уже имеющемуся индексу:

```dart
isReciprocal: _allEdges.containsKey((dst.id, src.id)),
```

(для форвардов/генеалогии — по `_addedEdgeEndpoints`; в DAG-графах взаимных пар быть не должно, флаг всегда `false`).

Дальше в `AnimatedHighlightedEdgePainter.paint`:

```dart
final offset = isReciprocal ? laneOffset : 0.0;     // laneOffset ≈ 4–6 dp
final a = src + n * offset;
final b = dst + n * offset;
// дуга: контрольная точка — середина, отведённая ещё на offset
final control = (a + b) / 2 + n * offset;
canvas.drawPath(Path()..moveTo(a.dx, a.dy)..quadraticBezierTo(control.dx, control.dy, b.dx, b.dy), paint);
```

Шейдер строится как `ui.Gradient.linear(a, b, …)` — по смещённым концам. Важное свойство линейного градиента: его изолинии перпендикулярны оси `a→b`, поэтому при заливке **дуги** блик всё равно бежит вдоль направления движения, а не «поперёк». Отдельный path-градиент не нужен.

### 4-bis.4 Что нужно проверить и предусмотреть

- **Фолбэк без анимации — закрыт стрелками (§4-bis.5).** `isAnimated` — поле `GraphState` (сейчас всегда `true`, менять его неоткуда), но при `MediaQuery.disableAnimations` / reduce-motion, а также в golden-тестах шейдер статичен, и направление в графе доверия исчезало полностью.
- **Величина смещения** должна зависеть от `strokeWidth`, иначе на ego-рёбрах (`strokeWidth: 3`) пути сольются. Ориентир: `laneOffset = strokeWidth * 2`.
- **Подписи и портреты.** Дуга уходит от центральной оси на `offset` в середине пролёта — при коротких рёбрах (соседние узлы одного кольца в `RadialHopLayout`) дуга может задеть портрет. Смягчение: ограничивать `offset` долей длины ребра (`min(laneOffset, length * 0.12)`).
- **Тест.** Golden-тест на пару взаимных рёбер: два path'а не пересекаются нигде, кроме окрестности узлов.

### 4-bis.5 Сделано: стрелки направления в графе доверия

Реализовано отдельным шагом, до остальных работ.

| Файл | Изменение |

| `graph_body.dart` | удалён геттер `_showEdgeDirection` (был `forwards \|\| genealogy`), painter получает `showDirection: true` — все три графа направленные |

| `l10n/app_en.arb`, `l10n/app_ru.arb` | новый ключ: «Arrows run truster → trusted; a mutual link has an arrow at each end» / «Стрелки: доверяющий → тот, кому доверяют; у взаимной связи стрелки с обеих сторон» |

**Почему взаимность читается уже сейчас, до разведения путей.** `_paintArrowhead` рисует чевron у **destination**-конца. Взаимная связь — это два ребра с противоположными концами, поэтому стрелки оказываются у разных узлов и **не накладываются друг на друга**, хотя сами линии пока лежат одна на другой. Читается так:

- стрелка на одном конце → одностороннее доверие;
- стрелки на обоих концах → взаимное.

То есть стрелки дают различение взаимного и одностороннего **раньше**, чем будет сделано разведение по путям; разведение (§4-bis.1–4) остаётся нужным, чтобы стали видны два встречных бегущих шейдера.

`kDefaultMinClientVersion` **не поднимался**: изменение чисто визуальное, старые клиенты остаются совместимыми.

## 5. K4 — взаимодействие и K5 — ограничения библиотеки

### 5.1 Перегруженный тап

`graph_body.dart:84-107`:

```dart
void _onNodeTap(NodeDetails node) {
  // второй тап по той же ноде в пределах 300 мс → переход на профиль/запрос
  // иначе → _graphCubit.setFocus(node)
}
```

а `setFocus` (`graph_cubit.dart:180-201`) делает сразу четыре вещи: меняет `state.focus`, дописывает `_focusPathIds`, пиннит ноду, и — если фокус тот же самый — уходит в `_fetch()` за следующей страницей соседей.

Итоговая ментальная модель, которую пользователь должен угадать сам:

| Действие | Что происходит |
|---|---|
| тап по новой ноде | выбрать + сфокусировать + подгрузить соседей + запиннить навсегда |
| тап по текущему фокусу | догрузить ещё 5 соседей |
| два тапа за 300 мс | уйти на экран профиля |

Тикет требует: «Define one click behavior for select/focus and one explicit control for expand». Предложение:

| Действие | Смысл |
|---|---|
| одиночный тап | **выбрать**: подсветить узел, показать панель действий (профиль / переслать запрос / раскрыть) — увязывается с уже сделанным #83 |
| кнопка «Раскрыть (N)» в панели | **раскрыть**: подгрузить соседей; N = `hiddenNeighborCounts[id]`, уже считается |
| двойной тап / кнопка в панели | перейти на профиль |
| долгий тап / правый клик | контекстное меню (см. память про cross-platform gesture affordances — long-press в одиночку нельзя) |

**Реализовано (tap intent, rev. 3):** маршрутизация тапа не использует badge `hiddenNeighborCounts` как сигнал «хочу раскрыть». Классификатор: `isCurrentFocus` → `canPageMore` (page more); иначе `everFocusedIds` → `selectNode` (rollback); иначе `expandNode` (first visit). Trust overview: origin при `focus==''` может page без смены focus. Genealogy: parent-chain сидится в `everFocusedIds` при bootstrap, чтобы тап по предку не вызывал лишний fetch children. Badge «ещё N» показывается на всех узлах с `hiddenNeighborCounts > 0` (не только у focus). `resetToEgo` не очищает `everFocusedIds`; `setContext` очищает.

Обратите внимание: `_doubleTapWindow` — это самодельный костыль, потому что `onDoubleTap` ломается из-за того, что первый тап заменяет ноду через `replaceNode` и сбрасывает распознавание жестов. Если убрать безусловный pin из `setFocus`, костыль становится ненужным.

### 5.2 Чего нет: Back / Reset to me / Fit current path

- **Back** — почти бесплатно: `_focusPathIds` уже хранит трейл, `_updateFocusPath` уже умеет обрезать хвост при возврате на уже посещённый узел (строки 260-263). Нужен метод `popFocus()` и кнопка.
- **Reset to me** — есть только `jumpToEgo()`, который двигает **камеру**, но не сбрасывает состояние (пины, трейл, накопленные `_allEdges`). Нужен настоящий reset: `_focusPathIds = [ego]`, снять все пины, пересчитать видимость. Полный `setContext(null)` слишком груб — он выкидывает кэш и передёргивает сеть.
- **Fit current path** — в библиотеке **нет** API «вписать прямоугольник в вьюпорт». Есть только `jumpToPosition` / `jumpToNode` / `zoomBy`. Патч **P4** в §6.

### 5.3 K5: почему нельзя обойтись без форка

1. **Алгоритм нельзя сменить после `initState`.** `_GraphViewState.initState` → `_initController()` → `controller._applyConfiguration(algorithm: widget.layoutAlgorithm, …)`, и `didUpdateWidget` **отсутствует** (`graph_view.dart:81-94`). Даже если приложение соберёт новый иммутабельный алгоритм, `GraphView` его проигнорирует. Следствие: нельзя иметь три раскладки для трёх графов, зависящие от режима, и нельзя пересчитать раскладку при смене фокуса.

2. **Алгоритму нельзя передать семантику.** Сигнатура — `layout({nodes, edges, size})`. Ни ego, ни focus, ни путь, ни направление обхода. Единственный канал — поля `NodeBase`, откуда и вырос `positionHint` (и его побочный эффект на `hashCode`).

   Патч P1 закрывает это элегантно: если алгоритм можно подменять на лету, то приложение просто конструирует `RadialHopLayout(root: egoId, focus: focusId, path: [...])` в `build()` — вся семантика едет внутри самого иммутабельного алгоритма, и отдельный «контекстный» параметр не нужен.

3. **Нет хука между «раскладка посчитана» и «раскладка отрисована».** См. §2.3.

4. **`clear()` оставляет контроллер в полумёртвом состоянии** (`controller.dart:306-312`): ставит `_layout = GraphLayout.empty()`, но не зовёт `_relayout()` и не сбрасывает `_centered`. После `setContext`/`togglePositiveOnly` камера уже не центрируется никогда.

5. **`_updateViewport` зовёт `notifyListeners()` из `InteractiveViewer.builder`**, то есть во время build (`controller.dart:220-236`, в коде честный комментарий-извинение). При `LazyBuilding.none()` (наш случай) `_effectiveViewport` всегда `Rect.largest`, так что рано или поздно ветка возврата срабатывает и повторных нотификаций нет — но это хрупко.

## 5-bis. Легенда как панель управления

**Решение (§10.5):** фильтр «скрыть негативные» унифицируется с легендой.

Сейчас `togglePositiveOnly` доступен из двух мест, и оба ущербны:

- `_GraphSideControls` — только при `windowClass == WindowClass.expanded` **и** только в неcompact-ветке `LayoutBuilder` (`graph_body.dart:130-136`), то есть **на телефоне панели нет вовсе**;
- popup-меню в AppBar — есть только на `GraphScreen`, но не на `ForwardsGraphScreen` и не на `InviteGenealogyScreen`.

При этом `GraphLegendPanel` лежит в `Positioned(left: 0, bottom: 0)` внутри общего `Stack` и потому **отображается во всех режимах и на всех ширинах**. Это готовая точка для унификации.

Предложение: строка легенды «негативная связь» (`graphLegendEdgeNegative`) становится переключателем видимости этого класса рёбер — как слои на карте. Тогда:

- фильтр становится доступен на телефоне (сейчас недоступен вообще);
- пропадает рассинхрон «легенда показывает красное ребро, а фильтр его скрыл» — образец в легенде и наличие рёбер на холсте управляются одним состоянием;
- модель расширяема: тем же механизмом позже включаются/выключаются «взаимные», «односторонние», «слабые» связи, ветви ego/target в генеалогии.

Технически это `GraphLegendContent` → `BlocSelector<GraphCubit, GraphState, bool>` на `positiveOnly` + `onTap` строки. Строки-переключатели визуально отличаются от справочных (приглушённый образец + `Switch`/чекбокс), чтобы не выглядело, будто кликабельна вся легенда. После этого пункт `togglePositiveOnly` уходит и из `_GraphSideControls`, и из popup'а AppBar.

Побочный эффект, который надо помнить: `togglePositiveOnly` в кубите сейчас делает **полный сброс** — `graphController.clear()`, `_fetchLimits.clear()`, `_allEdges.clear()`, сброс фокуса и трейла (`graph_cubit.dart:303-323`). То есть переключение фильтра из легенды выкинет весь прогресс исследования. После фазы 3 (когда `_allEdges` наполняется доборным запросом и `weight` известен для всех рёбер) фильтр должен стать **чистой операцией видимости** внутри `_recomputeVisibility`, без сети и без сброса — тогда он и станет честным «слоем карты».

## 6. Минимальные патчи в форк

Все патчи локальны, обратно совместимы (новые параметры с дефолтами), суммарно ≈250 строк. Ни один не требует трогать `EdgesView`/`NodesView`/`LabelsView`.

### P1 — сменяемая конфигурация (`graph_view.dart`, ≈25 строк) — **обязателен**

```dart
@override
void didUpdateWidget(covariant GraphView<N, E> oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (widget.layoutAlgorithm != oldWidget.layoutAlgorithm ||
      widget.canvasSize != oldWidget.canvasSize ||

    _initController();      // → _applyConfiguration, инкрементит _relayoutGeneration
  }
}
```

Требует, чтобы алгоритмы были иммутабельными value-объектами с `==`/`hashCode` — `GraphLayoutAlgorithm` уже помечен `@immutable`, а `FruchtermanReingoldAlgorithm` их не переопределяет (надо добавить, иначе будет relayout на каждый build). Отпирает: три разных алгоритма для трёх графов, и передачу ego/focus/пути внутрь алгоритма.

### P2 — переход между раскладками (`controller.dart` + `graph_layout.dart`, ≈120 строк) — **обязателен**

Суть: контроллер хранит `_displayedLayout` (то, что читает рендер) и `_targetLayout` (то, что посчитал алгоритм), и гонит первый ко второму по `Ticker`.

```dart
// graph_layout.dart
static GraphLayout lerp(GraphLayout a, GraphLayout b, double t, {
  Offset Function(NodeBase)? spawnPosition,   // откуда «выезжает» новый узел
}) { … }   // объединение ключей; отсутствующий в a → spawnPosition(node) ?? b-позиция
```

```dart
// controller.dart
Duration layoutTransitionDuration = Duration.zero;   // приходит из GraphView
Curve   layoutTransitionCurve = Curves.easeOutCubic;

void _publishLayout(GraphLayout next) {
  if (layoutTransitionDuration == Duration.zero || _layout == null) {
    _layout = next; notifyListeners(); return;
  }
  _from = _layout!; _target = next;
  _ticker.start();   // на каждый tick: _layout = GraphLayout.lerp(_from, _target, curve(t))
}
```

`TickerProvider` берётся из `_GraphViewState` (сделать `SingleTickerProviderStateMixin` и передавать в `_applyConfiguration`).

Дальше `graph_body.dart` ставит `showIterations: false` + `layoutTransitionDuration: 350ms` и получает ровно то, что просил заказчик: **алгоритм считает финальную раскладку целиком, затем граф одним управляемым переходом переезжает к ней**. Новые узлы «выезжают» из позиции узла, из которого их раскрыли, — соответствие сохраняется визуально.

Побочный выигрыш: 300–500 пересборок `CustomMultiChildLayout` заменяются на ~20 кадров интерполяции. На вебе это заметная разница.

### P3 — `fitToNodes` / `fitToRect` (`controller.dart`, ≈60 строк) — нужен для «Fit current path»

```dart
void fitToNodes(Iterable<NodeBase> nodes, {EdgeInsets padding = const EdgeInsets.all(48)});
void fitToRect(Rect rect, {EdgeInsets padding});
```

Вычисляет bounding box по `_layout`, с учётом `node.size`, подбирает масштаб в пределах `[minScale, maxScale]` и ставит матрицу `_transformationController`. Логика по сути уже есть в `jumpToPosition`, добавляется только расчёт масштаба. Заодно имеет смысл сделать анимированные варианты (`animateToNode`, `animateFitToNodes`) — при наличии тикера из P2 это ещё ~20 строк.

### P4 — честный `reset` (`controller.dart`, ≈15 строк) — мелочь, но без неё «Reset to me» кривой

```dart
void clear({bool recenterOnNextLayout = true}) {
  _nodes.clear(); _edges.clear();
  _layout = null;                        // а не GraphLayout.empty()
  if (recenterOnNextLayout) _centered = false;

```

и в `_applyConfiguration`/`_relayout` корректно обработать `_layout == null` (сейчас `_relayout` при `layout == null` молча выходит — после `clear()` граф не перестраивается вообще).

### P5 — опционально: `mutate(relayout: false)`

Позволяет кубиту сделать серию структурных правок и запросить пересчёт один раз. Убирает двойной relayout из §3.4. ≈10 строк, но требует дисциплины на стороне вызова.

Сейчас `Random(node.hashCode)` — детерминирован, но `initial_position_extractor.dart:44` в приложении заводит **глобальный `Random()` без сида** и подмешивает джиттер. При переходе на детерминированные алгоритмы этот файл просто уходит.

## 7. Варианты решения

### A. Косметика без форка

Что: `showIterations: false`, `iterations` вниз, `optimalDistance` вверх, снять безусловный pin, добавить Back/Reset через существующий `_focusPathIds`, `jumpToEgo` вместо fit.

- **Плюсы:** 1–2 дня, ноль риска, сразу убирает дрожание и большую часть тормозов.
- **Минусы:** узлы телепортируются; порядковая зависимость (§3.1–3.2) остаётся; направленная/слоёная раскладка невозможна; «Fit current path» невозможен; K3 не тронут.
- **Вердикт:** хорошая **первая неделя**, но не закрытие тикета.

### B. Детерминированные раскладки + минимальный форк ← **рекомендуется**

Что: патчи P1–P4; три алгоритма в приложении; серверный `graph_edges_between`; развод select/expand; Back/Reset/Fit.

- **Плюсы:** закрывает все четыре корня; каждый из трёх графов получает адекватную геометрию и свою легенду; раскладка становится **чистой функцией** от (узлы, рёбра, ego, focus, path) — то есть тестируемой в unit-тестах без виджетов; убирает `positionHint` вместе с его миной в `hashCode`.
- **Минусы:** 2.5–4 недели; нужен серверный кусок; нужно переписать ~40% `GraphCubit`.
- **Риск:** слоёная раскладка на графе доверия с циклами требует аккуратности (см. §8.3).

### C. Свой рендер поверх `CustomPaint` + `InteractiveViewer`

Что: выкинуть библиотеку, оставить только идею «layout → Map<id, Offset> → CustomMultiChildLayout».

- **Плюсы:** полный контроль; можно рисовать рёбра дугами/ортогонально, делать hit-testing по рёбрам, кластеризацию.
- **Минусы:** библиотека уже решает вполне нетривиальные вещи — lazy building по вьюпорту, layout-делегаты для узлов и подписей, координация матрицы `InteractiveViewer`. Переписывать это ради того же результата — 3–4 недели чистой инженерии без продуктовой ценности.
- **Вердикт:** не сейчас. Разумно как **эволюция** плана B: если алгоритмы уже чистые функции, замена рендера становится изолированным рефакторингом.

### D. Другая библиотека (`graphview`, `flutter_graph_view`)

- `graphview` даёт `BuchheimWalkerAlgorithm` (деревья) и `SugiyamaAlgorithm` (слоёные DAG) из коробки — это ровно то, что нужно генеалогии и форвардам. Но: рендерит через `Stack` без виртуализации, слабо кастомизируется по узлам, циклы Sugiyama обрабатывает разрывом рёбер, и **графа доверия с ego-центричной радиальной раскладкой там всё равно нет**.
- Пришлось бы либо тащить две библиотеки, либо всё равно писать свой алгоритм.
- **Вердикт:** нет. Но алгоритм Sugiyama/Coffman-Graham стоит **портировать** (≈200 строк) внутрь плана B для генеалогии и форвардов.

## 8. Что за алгоритмы писать (внутри плана B)

Все три реализуют `GraphLayoutAlgorithm`, все три — **чистые детерминированные функции**, `existingLayout` игнорируют (кроме как для spawn-позиции новых узлов через P2), результат зависит только от входа.

### 8.1 `LayeredDagLayout` — генеалогия и форварды

Классический трёхфазный Sugiyama в урезанном виде:

1. **Ранжирование** — longest-path от корня(ей). Генеалогия: корень = общий предок или узел ego. Форварды: корень = автор запроса.
2. **Упорядочивание внутри слоя** — barycenter-эвристика, 2–4 прохода вниз/вверх. Порядок узлов внутри слоя стабилизируется вторичным ключом (`id`), чтобы результат не зависел от порядка обхода `Set`.
3. **Расстановка координат** — `y = layer * layerGap`, `x` из порядка с центровкой поддеревьев.

Портреты не пересекаются по построению (слои разведены, внутри слоя шаг ≥ `nodeSize + gap`). Направление рёбер естественно читается сверху вниз.

Для генеалогии дополнительно: ветви `GenealogyEdgeBranch.ego` / `.target` разводятся по разные стороны от общего предка — вся нужная информация уже есть в `EdgeDirected.branch`.

### 8.2 `RadialHopLayout` — граф доверия

1. BFS по **неориентированной** проекции графа от ego → расстояние в хопах `d(v)`.
2. `radius = d * ringGap`; узлы с `d = 0` (ego) — в центре.
3. Угол внутри кольца: узлы сортируются по (угол родителя, score, id) и распределяются по сектору родителя — так поддерево «висит» под своим предком и кольца не перемешиваются.
4. Циклы не проблема: BFS-расстояние определено всегда, а ребро между двумя узлами одного кольца просто рисуется хордой.
5. Активный путь `_focusPathIds` притягивается к одному «лучу» (например, вверх), чтобы читался как хребет — требование «Keep the focused path stable while secondary nodes are added» выполняется буквально: пока путь не изменился, углы его узлов фиксированы.

Ключевое свойство: **позиция узла зависит только от его расстояния и предка, а не от того, когда его загрузили**. Раскрытие соседа добавляет узлы в следующее кольцо, не сдвигая уже существующие. Это и есть решение K2.

### 8.3 Риск: «стабильность vs. плотность»

Радиальная раскладка при большом количестве узлов в одном кольце даёт тесноту. Смягчения: (а) выделять сектор пропорционально размеру поддерева; (б) при переполнении кольца — второй «подслой» с чуть большим радиусом; (в) не показывать больше N соседей на раскрытие, оставляя бейдж `hiddenNeighborCounts` (уже реализован).

## 10. Принятые решения (ответы владельца продукта, 2026-07-29)

1. **Приватность рёбер — показывать можно.** Ребро X→Y отображается, даже если ни X, ни Y не ego: в этом и смысл exploration. `graph_edges_between` наследует текущее поведение `mr_graph`, дополнительной фильтрации не вводим.
2. **Потолок 100 строк в `mr_graph` оставляем**, offset наружу не прокидываем. Следствие: `mr_graph` окончательно закрепляется как **ранжирование** («кого показывать»), а полнота связности обеспечивается исключительно доборным `graph_edges_between` (§4.3). Это упрощает фазу 3: ни MeritRank, ни `graph()` не трогаем вообще.
3. **«Fit current path» при пути из одного узла** = вписать ego вместе со всеми его видимыми соседями.
4. **Направление в графе доверия — бегущий шейдер + стрелки.** Изначально решено обойтись шейдером, но после замечания о статичных кадрах (§4-bis.4) стрелки решено дорисовать. **Сделано** — см. §4-bis.5. Разведение взаимных рёбер по «путям» остаётся в работе.
5. **`positiveOnly` унифицируется с легендой** — строка «негативная связь» в легенде становится переключателем фильтра. Развёрнуто в §5-bis.
